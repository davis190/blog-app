# blog.claytondavis.dev

Source for [blog.claytondavis.dev](https://blog.claytondavis.dev): a [Hugo](https://gohugo.io) static site hosted on S3 + CloudFront, with a small serverless API (API Gateway, Lambda, SES) for the email list.

## How it fits together

```
git push to main
      │
      ▼
CodePipeline / CodeBuild  (aws/buildspec.yml)
      ├─ CloudFormation  aws/cloudfront.yaml   →  S3 bucket, CloudFront distribution, URL-rewrite function
      ├─ hugo build      content/ → public/    →  aws s3 sync
      ├─ SAM deploy      aws/infra/            →  email API + new-post sender (see below)
      └─ CloudFront invalidation (/*)
```

Everything in AWS is deployed from this repo by the pipeline. Don't change resources by hand.

The pipeline itself (CodePipeline `Blog-App`, CodeBuild `blog-app`, GitHub connection `Personal-Github`) is **not** defined in this repo; it was created by hand in 2022. Its source action has `DetectChanges` set to `true`, so a push to `main` should start it. If a push doesn't start a run, start one manually (it builds the latest `main`):

```bash
aws codepipeline start-pipeline-execution --name Blog-App --profile 210557127338_AWSAdministratorAccess --region us-east-1
```

`origin` uses the `github.com-davis190` SSH alias from `~/.ssh/config` so pushes authenticate as the repo owner.

## Email list

Lives in `aws/infra/` (`template.yaml`, code in `email-list/`). Subscribers are one address per line in `email-list.txt` in the `claytondavis-dev-email-list` bucket (versioned, never deleted with the stack).

**Subscribing is double opt-in:**

1. A visitor enters their address in the form at the end of a post. `POST /api/email/subscribe` emails them a confirmation link. **Nothing is added to the list yet.**
2. The link opens `/confirm/`, which shows a button. Clicking it calls `POST /api/email/confirm`, which adds the address and sends a welcome email (BCC to the owner).
3. Every email carries an unsubscribe link to `/unsubscribe/`, which also needs a button click before `DELETE /api/email/unsubscribe` removes the address.

The buttons exist so that mail security scanners that open links can't confirm or unsubscribe anyone.

**Signed links.** Confirm and unsubscribe links carry an HMAC-signed token (`common.py`), not a bare address, so nobody can act on an address they can't read mail for. The key is generated by CloudFormation in Secrets Manager (`rLinkSigningSecret`). **Don't rotate or delete it**: that invalidates the unsubscribe link in every email already sent. The token is signed, not encrypted, so it contains the address; that's why `/confirm/` and `/unsubscribe/` are `noindex`, send no referrer, and don't load analytics.

**Legacy links.** Emails sent before signed links existed contain `?email=<address>` unsubscribe links. They still work while `pAllowLegacyUnsubscribe` is `"true"` in `template.yaml`. Once you no longer care about those old emails, set the default to `"false"`.

**Abuse limits.** The API stage is throttled (2 requests/second, burst 5) because each subscribe request emails an address the caller chose.

### New posts are emailed automatically

`notify.py` runs at **9am, noon and 5pm Central** (`rNewPostNotifier`, an EventBridge Scheduler rule with an `America/Chicago` timezone, so the times hold across daylight saving). It reads the published RSS feed (`index.xml`) straight from the site bucket and emails each subscriber about any post it hasn't announced, then sends the owner a report. The email shows the post title and its front-matter `description`, so write that as the blurb you'd want in an inbox. Announced posts are recorded in `sent-posts.json` next to the subscriber list.

What to know:

- **It goes by the post's `date`**, not when you deploy. A post is announced on the next scheduled run after it's live. Only posts dated within `pNotifierMaxAgeDays` (3) are emailed; older ones are recorded as handled and skipped. That is what keeps it from emailing the whole back catalog on its first run, and it means a backdated post won't send. Use the manual function below for those.
- **At most once.** The post is recorded before sending, and automatic retries are off. If a run dies midway, the next run will not resend; subscribers it missed need a manual send.
- **Drafts and future-dated posts** aren't in the feed, so they're never emailed.
- **Dry run:** set `pNotifierDryRun` to `"true"` to log what would be sent without sending or recording anything.
- **To skip emailing a post,** there is no flag yet. Add its link to `sent-posts.json` in the bucket before the next scheduled run.

### Sending a one-off email

For anything that isn't a new post, invoke the `sendEmail` function (name is in the stack outputs: `aws cloudformation describe-stacks --stack-name blog-email-subscription --query "Stacks[0].Outputs"`):

```json
{
  "subject": "Subject line",
  "body": "<p>HTML body. An unsubscribe footer is added for you.</p>"
}
```

## Repository layout

| Path | Purpose |
| --- | --- |
| `content/post/NNN-slug/` | One folder per post: `index.md` plus its images |
| `content/about.md`, `confirm.md`, `unsubscribe.md` | Standalone pages (the last two use the `email-action` layout) |
| `layouts/` | Templates. Started as the [hugo-ink](https://github.com/knadh/hugo-ink) theme, copied in and modified; there is no `themes/` directory |
| `static/` | CSS, JS, images served as-is (`js/subscribe.js` drives the subscribe box and the confirm/unsubscribe pages) |
| `aws/` | Pipeline, CloudFront, and email infrastructure |
| `config.toml` | Site config: menu, social links, favicon, related-post settings |

## Local development

```bash
brew install hugo
hugo server -D      # http://localhost:1313, includes drafts
```

CodeBuild pins **Hugo 0.93.3** (`aws/buildspec.yml`). The templates are kept compatible with both that version and current Hugo, so a local build on either should match production. If you change a template, build with the pinned version too, since that is what actually deploys.

Post links in templates end in `/index.html`. Bare URLs such as `/post/slug/` work too: a CloudFront Function (`rIndexRewriteFunction`) maps them to the page's `index.html`. This is what makes the RSS feed, sitemap, and link previews point at real pages.

## Writing a post

```bash
hugo new post/013-my-post-slug/index.md
```

Front matter:

```yaml
---
title: "Post title"
date: 2026-01-01T08:00:00-06:00
draft: false
description: "One sentence. Shown on the home page and used for the link preview."
tags: [GenAI, AI-SDLC, Product]
---
```

- **Feature image:** drop an image named `feature-<anything>.png` in the post folder. Hugo's Open Graph template picks up `feature*` files automatically for link previews (LinkedIn, Slack, etc.). Without one, the site logo is used. The image is not shown in the post body; add `![alt](file.png)` for that.
- **Tags:** reuse existing tags and spell them the same way (`AI-SDLC`, not `AI SDLC`). Tags that differ only by spaces or hyphens collide on the tag page URL. Tags also drive the "Keep reading" suggestions at the bottom of each post.
- **Raw HTML** in Markdown is dropped by Hugo's renderer. Use Markdown syntax (`*italic*`, not `<em>`).
- **Reading time** and **newer/older** links are generated automatically.
- **`date` matters:** it's the publish date shown on the site and the date the email sender uses (see above). Set it to when you intend to publish.

### Drafts stay private

The pipeline runs plain `hugo`, so a post with `draft: true` is never published or emailed. Flip it to `false` to publish. (`hugo server -D` shows drafts locally.)

## Publishing

Merge to `main`. The pipeline builds, syncs to S3, deploys the email stack, and invalidates the whole CloudFront cache. Subscribers are emailed about the new post at the next 9am, noon or 5pm Central run.

## Components worth knowing about

- **Subscribe box** (`layouts/partials/subscribe.html`) is included on posts, the home page, and list pages. Set `subscribe: false` in a page's front matter to hide it.
- **Pages with sensitive URLs:** front matter `noindex: true` adds robots/no-referrer tags and `analytics: false` skips Google Analytics. The confirm and unsubscribe pages use both.
- **Dark mode** follows the visitor's OS setting; the toggle in the header overrides it and is remembered in the browser (`static/js/main.js`).
- **Favicons** in `static/images/` are generated from the avatar (`favicon.png` 64px, `apple-touch-icon.png` 180px).
